# 可视化计算器 · 前端设计说明

> 这份文档记录**为什么这样设计**，而不是代码在做什么（代码自己会说）。
> 主要供作业博客「设计思路」与答辩问答使用。

---

## 一、需求理解：前端到底该做什么

助教作业帖把前后端职责划得很清楚。落到前端，真正的要求是：

| 前端**应该**做 | 前端**不应该**做 |
|---|---|
| 界面呈现、按钮交互、表达式输入 | 解析表达式 |
| 把表达式发给后端 | 计算优先级、括号、正负号 |
| 显示后端返回的结果 | 判断除零 |
| 显示后端返回的错误 | 自己编造结果或错误文案 |
| 历史记录的展示与删除请求 | 把历史存在 LocalStorage 里 |

**验收时的判定方法**（作业帖原话）：停掉后端服务，"前端可以继续接受输入与正常交互，
但不能独立获得新的有效计算结果"。

这条要求直接决定了整个架构：**前端连一个加法都不能算**。
所以本仓库 `src/js/` 里搜不到任何算术表达式，`=` 键在后端接通前只给提示、不给结果。

## 二、模块划分与职责边界

```
        ┌──────────────────────────────────────────────┐
        │  calc-buttons.js   事件驱动（唯一分发中心）    │
        │  · 事件委托：整个键盘区一个 click 监听器       │
        │  · 按键分发、= 键的提交逻辑                    │
        └───────┬──────────────────────────┬───────────┘
                │ 调用                      │ 调用
                ▼                          ▼
   ┌────────────────────────┐   ┌────────────────────────┐
   │  input-model.js        │   │  ui.js                 │
   │  表达式缓冲区（纯函数）  │   │  渲染层（唯一操作 DOM） │
   │  · 六类输入校验         │   │  · 显示屏、光标、提示条 │
   │  · 不碰 DOM、不计算     │   │  · 按键高亮与按下反馈   │
   └────────────────────────┘   └────────────────────────┘
                ▲
                │ 复用同一入口
   ┌────────────────────────┐
   │  keyboard.js           │
   │  物理键盘 → 按键语义    │
   │  · 不含任何输入规则     │
   └────────────────────────┘
```

**三条边界规则**：

1. **只有 `ui.js` 可以碰 DOM。** 其他模块负责算出"现在该显示什么"，不负责怎么显示。
   好处：界面不一致时只有一个地方要找。
2. **只有 `input-model.js` 决定输入是否合法。** 其余模块不许自己判断
   "这个字符能不能输入"。好处：规则只有一份。
3. **鼠标和键盘走同一个入口。** `keyboard.js` 只做"按键 → 语义"的翻译，
   翻译完交给 `calc-buttons.js` 的 `handleKey`。好处：不可能出现
   "点击禁止、键盘却能输入"的不一致。

> 反过来看：如果要加一个"科学计算"面板，只需要在 `input-model.js` 增加规则分支，
> 另外两个文件基本不动。这就是划分边界的收益。

## 三、增量交付：三个可运行版本

课程近期在讲敏捷、极限编程，其中两条直接影响开发顺序：
**「基础功能必须在首版完成，增量分组要考虑依赖关系」**（新纪要）与
**「Keep It Simple」**（XP 编码实践）。据此把前端切成三个**都能打开运行**的增量：

| 增量 | 内容 | 打开页面能看到什么 | 依赖关系 |
|---|---|---|---|
| **v0.1** | `index.html` + `style.css` | 完整界面，能看不能点 | 无（是后面两个的基础） |
| **v0.2** | `input-model.js` + `ui.js` + `calc-buttons.js` | 能点、有颜色反馈、有输入校验 | 依赖 v0.1 的结构与类名 |
| **v0.3** | `keyboard.js` + 错误提示条 | 鼠标与键盘都能用，错误有中文提示 | 依赖 v0.2 的处理入口 |

**为什么这样切**：v0.1 是"界面骨架"，它决定了 CSS 类名，而 v0.2 的 JS 要靠这些类名
去查元素 —— 所以界面必须最先稳定，这是真实的依赖关系，不是为了好看才这么分。
v0.3 之所以放最后，是因为它**复用** v0.2 建好的入口，如果反过来先做键盘，
就会被迫写两套规则，之后还得合并。

每个增量结束时页面都是**可运行**的，随时可以截图为证 —— 这也是"可运行软件是衡量进度的首要标准"
（敏捷十二原则之一）在本项目里的落地。

## 四、关键设计决策

### 决策 1：用事件委托，不用 27 个 onclick

整个键盘区只挂一个 `click` 监听器，用 `event.target.closest('[data-key]')` 定位被点的按钮。

| 方案 | 优点 | 缺点 |
|---|---|---|
| 27 个按钮各挂监听器 | 直观 | 加键要改 JS；规则散在 27 处；内存占用大 |
| **事件委托（本方案）** | 一个入口、加键不改 JS、动态元素也有效 | 处理函数里多一步 `closest()` 判断 |

选后者的决定因素不是"写法高级"，而是**规则集中**：所有按键最终都调用同一个
`handleKey`，不可能出现某个按钮漏了校验的情况。

### 决策 2：颜色变化用 CSS 伪类 + JS 状态类两条路径

老师点名的需求是"按钮点击触发颜色变化"。这里刻意用了两种实现并写进注释：

| 实现 | 代码 | 能覆盖的场景 |
|---|---|---|
| CSS 伪类 | `.key:hover` / `.key:active` | 鼠标悬停、鼠标按住 —— **不写一行 JS** |
| JS 状态类 | `.is-pressed` / `.is-armed` | ① 物理键盘按下时也高亮（键盘没有 `:active`）② 运算符键在鼠标移开后仍保持高亮 |

结论：**能用 CSS 表达的就不写 JS；CSS 表达不了的才用状态类**。
这是"最小必要复杂度"的具体应用。

### 决策 3：表里分离 —— 界面显示 `×` `÷`，内部存 `*` `/`

老师课件里明确写了这个约定（"用户界面可以显示 × 和 ÷，内部表达式用 * 和 /"）。实现方式：

- 内部一律存 ASCII 字符 `*` `/` `-`；
- 只在**渲染前**做一次映射（`ui.js` 的 `toDisplayText`）；
- 映射是一对一替换，字符数不变，所以光标位置不受影响。

好处：表达式可以直接发给后端，不需要在提交前"翻译"一遍；也不存在"界面符号漏进表达式"
导致后端解析失败的风险。

### 决策 4：正负号写成 `(-数字)` 而不是插一个 `-`

按 `±` 时，`5+3` 变成 `5+(-3)`，而不是 `5+-3`。

后者虽然很多解析器能接受，但它的合法性依赖解析器的宽容度；
写成前者以后，**任何**符合常规语法的解析器都能无歧义处理。再按一次 `±` 则整体还原成 `5+3`。

这条设计直接影响后端：后端的词法分析器可以要求"运算符后面必须跟数字或左括号"，
而不必额外为 `+-` 这种组合开口子。

### 决策 5：连续运算符"替换"而不是"追加"

输入 `1+*` 时，结果是 `1*` —— 新运算符**替换**掉刚输入的那个。

这是真实计算器的常见行为，同时顺手消解了一个棘手问题：
如果不做替换，就必须决定"连续两个运算符"是否合法，而一旦合法，
表达式校验就要处理 `1++2`、`1+/2` 这类边界。替换之后，非法组合在输入端就不再产生。

例外：`3*-2` 这种**负号**是允许的 —— 判据是"前一个运算符不是减号时，
再输入减号视为负号"。这让一元负号与二元减号在输入阶段就能区分开。

### 决策 6：纯函数式缓冲区

`applyKey(state, key)` 不修改传入的 `state`，而是返回新对象。
返回值里带 `message` 与 `messageType`，界面层直接照它渲染。

收益：
- 规则可以脱离浏览器测试 —— `src/test/test-input-model.js` 就是直接跑这个函数，
  49 条断言几毫秒跑完，不需要启动页面。
- "输入被拒绝"只有一种实现（`reject` 函数），不会出现某个分支改了文本却没给提示。

## 五、异常处理分工

| 异常类型 | 由谁判断 | 前端表现 |
|---|---|---|
| 非法字符、连续运算符、多个小数点 | **前端**（输入阶段拦掉） | 提示条变红，输入不写入 |
| 括号不配对、以运算符/小数点结尾 | **前端**（提交前校验，`canSubmit`） | 提示条变红，不发送请求 |
| 除零 | **后端** | 把后端返回的 `DIVISION_BY_ZERO` 译成「除数不能为 0」 |
| 表达式语法非法（前端没拦住的） | **后端** | 显示后端返回的 `INVALID_EXPRESSION` 提示 |
| 网络不通 / 后端未启动 | 前端（`fetch` 失败） | 提示"无法连接后端服务" |
| 服务器内部错误 | 后端 | 显示 `INTERNAL_ERROR` 的通用提示 |

**原则**：前端只拦它**能确定**的错误（字符层、结构层），
**语法与语义层的判定权交给后端**。前端不做"猜后端会不会报错"的事，
否则两边规则一旦不一致，就会出现"前端说非法、后端说合法"的矛盾。

`ui.js` 里的 `SERVER_ERROR_TEXT` 就是这张分工表的落地：错误码 → 中文提示。

## 六、自测设计

`src/test/test-input-model.js` 用 Node 内置断言，零依赖，覆盖 49 条：

| 分组 | 条数 | 覆盖内容 |
|---|---|---|
| 基本输入 | 8 | 数字、多位数、四则、小数 |
| 开头限制 | 4 | 不能以 `+ * /` 开头，允许 `-` |
| 连续运算符 | 4 | 替换行为、负号、同类运算符 |
| 小数点 | 5 | 重复小数点、前导零、跟在右括号后 |
| 括号 | 6 | 配对、非法位置、隐式乘法 |
| 正负号 | 4 | 加括号、再按还原、空表达式拒绝 |
| 退格与清空 | 5 | 单字符退格、整个负号组退格、AC |
| 长度上限 | 1 | 超长截断在 60 |
| 辅助函数 | 4 | 末尾数字提取、括号统计 |
| 提交校验 | 6 | 各类不可提交情形 |
| 白名单 | 2 | 不支持按键被拒 |

**为什么必须写**：输入规则是最容易"改一处坏一处"的地方，而它的问题在界面上不一定马上显现
（比如某个合法输入被悄悄拒绝）。把这些规则写成断言，改完跑一遍，几秒钟就知道有没有踩坏东西。

## 七、本轮明确不做的事

| 不做 | 原因 |
|---|---|
| 后端与数据库 | 按课程安排，本轮是前端阶段 |
| 结果计算 | 作业要求结果必须由后端产生 |
| 历史记录的真实数据 | 后端未接通；右侧区域只放说明文字，**不放演示假数据** |
| 部署 | 前端单文件可直接打开，正式部署在联调阶段与后端一起做 |

> 右侧历史区"宁可空着说明，也不放假数据"是刻意的：
> 截图与演示必须对应真实实现，放静态假数据会在助教核对时暴露。
